## Requirement understanding

One line: Don wants autotask_search_contacts to return each contact's user-defined fields and to find a contact by an exact match on any of its three email fields (emailAddress, emailAddress2, emailAddress3), so PRECICOM's offboarding agent can run its authorization check without needing the unrestricted autotask_raw_request tool.

PRECICOM's offboarding agent must check, before touching Microsoft 365, that the person submitting an offboarding request is an active Autotask contact whose role field says "decision-maker," and that the submitter and the departing contact belong to the same active company; either person's email may live in any of the three Autotask contact email fields. Today the only tool that can read a contact's user-defined fields or match a non-primary email is `autotask_raw_request`, an unrestricted pass-through that can also create, update and delete records; instruction text alone cannot enforce read-only use of it. Success is `autotask_search_contacts` alone being enough for this lookup, so `autotask_raw_request` can be switched off for this agent. Route B (a per-agent method/entity allowlist on `autotask_raw_request`) was in the original intake but was explicitly triaged out of scope for this ticket (comment by Micus, 2026-10-30: "Route B ... is not in scope").

## Product design

### Goals / Non-goals

Goals:
- `autotask_search_contacts` can find a contact by an **exact** match on any of `emailAddress`, `emailAddress2`, `emailAddress3`.
- A contact found this way still includes `companyID` and `isActive` (already true today — confirmed, no regression).
- Calling the tool with `includeUserDefinedFields=true` (existing, unchanged parameter) still returns `userDefinedFields` so the caller can read the role value.
- Existing `searchTerm` fuzzy search keeps behaving exactly as it does today.

Non-goals:
- Route B (a per-agent method/entity allowlist on `autotask_raw_request`) — out of scope per the 2026-10-30 triage comment.
- Server-side filtering of results by a specific user-defined-field value (e.g. role = "Decision-maker"). The ticket's own Interview Log states this "is not needed for deployment": the full `userDefinedFields` list is already returned via the existing `includeUserDefinedFields=true` flag, so the calling agent already has everything it needs to read the role value itself. This is a design decision, not an unresolved question — see "Done when #3" handling below.
- Actually switching off `autotask_raw_request` for any agent or tenant — that is a connector/role configuration action on the Agent Platform, done once this capability ships; it is not a code change in this repo.

### Acceptance criteria AC1..ACn

- **AC1**: Given a contact whose target email is stored in `emailAddress`, `emailAddress2`, or `emailAddress3`, when `autotask_search_contacts` is called with an exact-match email filter equal to that value, then that contact is returned. A value that is only a substring of a stored email (not an exact match) returns nothing.
- **AC2**: Given a contact found this way, when `includeUserDefinedFields=true` is also passed, then the result includes `userDefinedFields` with names and values (existing behavior, confirmed unaffected by the new filter).
- **AC3**: Given a contact found this way, then `companyID` and `isActive` are present in the result when set on the record (existing behavior, confirmed unaffected).
- **AC4**: Given the existing `searchTerm` parameter, when used without the new email filter, then matching is unchanged: contains-match against `firstName`, `lastName`, `emailAddress` only (not `emailAddress2`/`emailAddress3`), and every other existing tool call shape still works exactly as today.
- **AC5** (Done-when item 3 — "optional filter by a user-defined field value ... works, or the card says why not"): **why not** — the ticket's own Interview Log says this filter is not required for deployment, because the full `userDefinedFields` list returned under AC2 already lets the calling agent read the role value and decide for itself; adding a server-side UDF-value filter would be new, unrequested surface for a need the agent can already meet. If a future ticket asks for it, it is a separate additive parameter.
- **AC6** (composite, Done-when item 4 / "the offboarding authorization lookup works with autotask_raw_request disabled"): Given AC1, AC2 and AC3 all hold, when PRECICOM's offboarding agent looks up the submitter and the departing contact by email, reads the submitter's role from `userDefinedFields`, and compares `companyID`/`isActive` on both, then the whole check completes using only `autotask_search_contacts` — no call to `autotask_raw_request` is needed.

### Open questions

- [assumed, not blocking] Whether Autotask's `eq` query operator compares email strings case-sensitively was not independently verified — no live Autotask test connection was available during design (the ticket's own "Existing Capability Check" section says the same: "current connector coverage was not independently verified"). Assumed safe to ship as a plain `eq` match, consistent with how every other exact-match filter in this repo is built (`api.py:422-439`); if the dev leg's self-test against a real zone shows case sensitivity is an issue, it is a small, localized fix (case-normalize before filtering) and does not change the tool's shape or this design's conclusions.
- [not blocking] Whether the new email filter should accept a list of addresses in one call was not asked for and is not needed for the stated use case (one submitter + one departing contact per offboarding run); can be added later as an additive parameter if requested.

## Tech design

### Conclusion

Add one optional parameter, `email`, to the existing `autotask_search_contacts` tool in `src/autotask_mcp/tools/contacts.py`. When set, it builds an OR'd exact-match (`eq`) filter across `emailAddress`, `emailAddress2`, and `emailAddress3`, ANDed with the existing `companyID`/`isActive` filters — the same `any_of`/`build` pattern this file and three sibling tool files already use for "match any of several fields." Nothing else in the repo changes: no new dependency, no schema or migration (this service has none — it is a stateless proxy to Autotask's REST API), no gateway change, single repo.

### Where the current implementation lives

- `src/autotask_mcp/tools/contacts.py:42-80` — `autotask_search_contacts` tool definition and handler (the only place this ticket touches).
- `src/autotask_mcp/tools/_common.py:172-186` — generic `search()` helper; reused unchanged.
- `src/autotask_mcp/api.py:323-339` (`AutotaskClient.query`), `:347-383` (`AutotaskClient.search`, paging) — the REST client; confirms `IncludeFields` is only sent when explicitly requested, so Contacts search already returns the full default field set.
- `src/autotask_mcp/api.py:422-439` — `eq`, `op`, `any_of`, `build` filter helpers; the established "match any of several fields" pattern, already used at `contacts.py:78`, `companies.py:243`, `time_entries.py:62`, `tickets.py:154`.
- `tests/test_handlers.py:269-278` — existing UDF-opt-in test (`test_search_contacts_hides_udfs_by_default`), extended by this change rather than replaced.
- `tests/test_tools.py:30-41` + `tests/fixtures/tools_baseline.json` — the 111-tool backward-compatibility contract every change must keep passing.

### Option analysis

| Option | Approach | Pros | Cost | Verdict |
|---|---|---|---|---|
| A. New `email` parameter, exact `eq` OR'd across the 3 fields | Add `Opt("email", str, ...)`; build `any_of(eq(emailAddress), eq(emailAddress2), eq(emailAddress3))`, AND with existing filters | Minimal; keeps `searchTerm`'s fuzzy semantics completely unchanged (AC4); follows the repo's own `any_of` pattern | One more optional parameter on an already large tool | **Chosen** |
| B. Overload `searchTerm` to also try exact match on the 3 email fields when the term looks like an email | No new parameter | Smaller API surface | Silently changes existing `searchTerm` behavior for any caller who already passes a full email address (today they get a contains match that can also hit other fields; switching email-shaped input to exact-only changes results for existing callers) — risks AC4 and the spirit of the baseline compatibility test, not just its letter | Rejected |
| C. New dedicated tool, e.g. `autotask_find_contact_by_email` | Separate tool | Very explicit | The README states all 111 tool names intentionally match the previous connector for platform compatibility; a new tool duplicates paging/companyID/isActive/UDF logic that `autotask_search_contacts` already has | Rejected |

### Data & API contract

- MCP tool request (new field only, all others unchanged):
  ```json
  {"email": "jane.doe@example.com"}
  ```
  Combinable with the existing `companyID`, `isActive`, `page`, `pageSize`, `includeUserDefinedFields`.
- Response shape unchanged: `{"items":[...],"count":n,"page_number":n,"page_size":n,"has_more":bool}`. Each item is a Contact record with every non-null field Autotask returns by default — `emailAddress`, `emailAddress2`, `emailAddress3`, `companyID`, `isActive` included whenever set on the record — plus `userDefinedFields` only when `includeUserDefinedFields=true` (unchanged, `contacts.py:79`).
- Backward compatibility: `email` is optional and purely additive. Omitting it reproduces today's behavior byte-for-byte (identical filters list, identical `any_of` usage for `searchTerm` only). No database, no migration — this service holds no state of its own; it is a stateless HTTP proxy to the Autotask REST API.
- Downstream Autotask call: `POST /Contacts/query` gains one more OR'd `eq` clause group in its `Filter` array — the same query mechanism every other tool in this repo already uses (`api.py` module docstring, "Queries" section).

### Key flow / sequence

PRECICOM offboarding agent calls `autotask_search_contacts(email=<submitter email>, includeUserDefinedFields=true)` → server builds an `eq` filter OR'd across the 3 email fields, ANDed with any `companyID`/`isActive` filters → `POST /Contacts/query` to Autotask → contact record (with `userDefinedFields`) returned → agent reads the role UDF value and `companyID`/`isActive` → agent repeats the call for the departing contact's email → agent compares `companyID` and checks both `isActive`, then decides whether to proceed to Microsoft 365 → `autotask_raw_request` is not called at any point in this flow and can be disabled for this agent's role.

### Non-functional

- **Idempotency/concurrency**: pure read; `autotask_search_contacts` already carries `readOnlyHint=True` (`tests/test_tools.py:63-67`). No state change, safe to retry, unaffected by this addition.
- **Performance**: adds two more `eq` clauses OR'd into the same single `/Contacts/query` call — no additional round trip, same page size (default 25, capped 200).
- **Security**: no new credential handling; the email value flows through the same per-request `AutotaskClient`/`Credentials` ContextVar as every other filter (`credentials.py`) — never logged, never cached across requests (`AGENTS.md` rule, unchanged). The net security effect of this change is positive: it is what lets PRECICOM disable `autotask_raw_request` (which can also create/update/delete) for this read-only agent.
- **Multi-tenant isolation**: unchanged. Every call still carries the caller's own `X-Api-Key`/`X-Api-Secret`/`X-Integration-Code`/`X-Api-Url` headers via the per-request ContextVar; the new filter executes inside the same tenant-scoped Autotask query as today. TC-ATC-011 verifies the new code path adds no shared state across two different tenants' requests.
- **Observability**: no new logging needed; errors from this tool continue to use the existing structured envelope (`not_configured`/`unauthorized`/`not_found`/`invalid_argument`/`rate_limited`/`upstream_error`, per README "Behaviour notes").

### Rollout & rollback

No feature flag — this is a stateless MCP tool with no persisted state. Rollout is "merge to `main`, publish to INT" per `references/mcp-track.md`; rollback is redeploying the previous `main` sha, with no data to migrate back. Single-repo change (`Track: vendor-mcp`, `MSPbotsAIFramework/autotask-mcp` only) — no cross-repo release-order dependency; nothing in the gateway or platform needs to change before or after this.

### Test strategy

Integration tests in `tests/test_handlers.py` (respx-mocked Autotask API, following the existing `test_search_contacts_hides_udfs_by_default` pattern): exact match on `emailAddress2`, exact match on `emailAddress3`, a negative case proving the match is exact (not a `contains` fallback), a no-match case, combination with `companyID`/`isActive`/`includeUserDefinedFields`, and a regression case proving plain `searchTerm` behavior is unchanged. `tests/test_tools.py`'s baseline/backward-compatibility suite must keep passing unmodified. The one case needing a real Autotask test connection (TC-ATC-010, end-to-end against a live zone) is out of local test reach and is recorded in the ac.json as "needs a real vendor account" — per `references/mcp-track.md` section 3, that does not block design, dev, or review.

### Effort & breakdown

Single, atomic change: one function, a handful of new test cases, one README line. Estimate 0.5–1 day including dev-side tests and self-test gates. Not worth splitting into sub-tasks.

### Risks & dependencies

- **Risk**: Autotask's `eq` operator's case sensitivity on string fields was not independently verified during this read-only design pass (no live Autotask connection available — see Open Questions). Mitigation if it turns out to matter: a small, localized case-normalization change during dev's self-test against a real zone; it does not change this design's shape or conclusions.
- **Dependencies**: none. Single repo, no gateway change, no other open ticket blocks this.
