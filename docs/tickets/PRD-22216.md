## Requirement understanding

One line: Don reports that autotask_get_ticket_attachment returns not_found for every attachment that autotask_search_ticket_attachments lists (also with includeData false) and wants it fixed to return the attachment metadata, and the file content when includeData is true.

Forte Technologies' onboarding agent must read the "New Employee Technology Checklist" PDF attached to hire tickets, and cannot today. Reproduced by the reporter on four Forte attachments (tickets 1556310 and 1546276) and on the MSPbots demo Autotask (ticket 9111, attachment 46). Success: the tool returns the record for any attachment the search tool lists, with base64 content when includeData is true. The reporter's hypothesis (the tool expects a single `item` object but Autotask returns an `items` list) is checked against code below.

- `autotask_search_ticket_attachments` works because it uses the query endpoint, which is parsed as `items` (`api.py:337-338`).

## Product design

### Goals / Non-goals

Goals:
- `autotask_get_ticket_attachment` returns the metadata of any attachment listed by `autotask_search_ticket_attachments`, with `includeData` false or true.
- With `includeData=true` it also returns the base64 `data` (unchanged size cap and `dataOmittedReason` behavior).
- The same fix applies to `autotask_get_ticket_note_attachment`, which shares the code path.

Non-goals:
- No new tool, no renamed tool, no removed or newly required parameter (AGENTS.md, `tests/test_tools.py` baseline).
- No change to the ownership check (an attachment that belongs to another ticket still returns not_found).
- No change to attachment creation or search.

### Acceptance criteria AC1..ACn

- **AC1**: Given an attachment listed by `autotask_search_ticket_attachments`, when `autotask_get_ticket_attachment` is called with that ticket and attachment id and `includeData` omitted or false, then the attachment metadata is returned and there is no error, even when Autotask returns the record inside an `items` list.
- **AC2**: Given the same attachment, when `includeData=true`, then the result contains the metadata and the base64 `data` (or `dataOmittedReason` plus `dataLength` when above `maxInlineBase64Bytes`), even when Autotask returns the record inside an `items` list.
- **AC3**: Given an attachment id that belongs to a different ticket, when the tool is called with another ticket id, then the result is a `not_found` error.
- **AC4**: Given an attachment id that does not exist (Autotask returns an empty `items` list or 404), when the tool is called, then the result is a `not_found` error.
- **AC5**: Given Autotask answers with the single-object shape `{"item": {...}}`, when the tool is called, then it still works exactly as today (no regression).
- **AC6**: Given a ticket note attachment, when `autotask_get_ticket_note_attachment` is called, then it behaves as AC1 and AC2 for both response shapes.

### Open questions

- [assumed, not blocking] Autotask's actual response shape for `GET /{Entity}/{id}` was taken from the reporter's raw output (`items` list), not re-verified live. The design accepts both shapes, so it is correct either way.
- [not blocking] Whether Autotask returns more than one element in `items` for a by-id GET is unknown; the design picks the element whose `id` equals the requested id and falls back to the first.

## Tech design

### Conclusion

Confirm the reporter's hypothesis as the root cause and fix it once in the shared client: `AutotaskClient.get_item()` (`api.py:316-321`) accepts both `{"item": {...}}` and `{"items": [...]}`. `_attachment()` reuses one small helper for its parent-scoped metadata read instead of its own `payload["item"]` parsing. Every tool that uses `get_item()` is fixed with it.

### Where the current implementation lives

- `src/autotask_mcp/tools/attachments.py:33-50` — `_attachment()`: the two read paths (`get_item`, parent-scoped GET) both parse only `item`.
- `src/autotask_mcp/api.py:316-321` — `AutotaskClient.get_item()`: raises the reported not_found when `item` is absent.
- `src/autotask_mcp/api.py:337-338` — the query path already reads `items` (pattern to follow).
- `tests/test_handlers.py:544-556` — the existing attachment test (only the `item` shape).

### Option analysis

| Option | Approach | Pros | Cost | Verdict |
|---|---|---|---|---|
| A. Shared helper `single_record(payload, record_id)` in `api.py`, used by `get_item()` and `_attachment()` | One place knows both shapes | Fixes all by-id reads, no duplication | One small function | **Chosen** |
| B. Patch only `_attachment()` | Local `items` handling | Smallest diff | Leaves the same defect in the other by-id tools; duplicates parsing | Rejected |
| C. Switch attachment reads to `/TicketAttachments/query` with an `id` filter | Reuse the query parser | Uses a path known to return `items` | Extra request shape, larger response with data, behavior change for `includeData` | Rejected |

### Change list

- `src/autotask_mcp/api.py` **[changed]** — add `single_record(payload, record_id=None) -> dict | None`: return `payload["item"]` when it is a non-empty dict; else when `payload["items"]` is a non-empty list return the element whose `id` equals `record_id`, falling back to the first element; else `None`. `get_item()` uses it and still raises the same not_found when it returns `None`. Update the module docstring line at `api.py:11` to state both shapes.
- `src/autotask_mcp/tools/attachments.py` **[changed]** — replace `(payload or {}).get("item")` (`:41`) with `single_record(payload, att_id)`; import it from `..api`. No other change: the ownership check, data cap and output shape stay.
- `tests/test_handlers.py` **[changed]** — add the cases in `docs/tickets/PRD-22216.ac.json`.
- `docs/changes/2026-11-16-attachment-read-items-shape.md` **[new, dev leg]** — changelog entry per `AGENTS.md`.
- `tests/test_tools.py` / `tests/fixtures/tools_baseline.json` **[no change needed]** — no tool or parameter changes.

### Reuse & cleanup

- **Reuse**: `get_item()` stays the single by-id entry point; `clean`, `item_id`, `_json.dump` unchanged.
- **New dependencies**: none.
- **API/method signatures**: one new module-level helper `single_record`; `get_item()` signature unchanged; no tool signature changes.
- **In-scope cleanup**: the inline `(payload or {}).get("item")` in `attachments.py:41` is removed in favor of the helper; no other dead code found in the touched files.
- **Suggested follow-ups (out of scope)**: none observed.

### Data & API contract

- Tool request and response are unchanged: `{"ticketId": 1556310, "attachmentId": 1975897, "includeData": true}` returns the attachment record fields (plus `data`, or `dataOmittedReason` and `dataLength`).
- Downstream Autotask calls are unchanged: `GET /Tickets/{id}/Attachments/{attId}` and `GET /TicketAttachments/{attId}`; only the parsing of the response changes.
- Backward compatibility: `{"item": {...}}` responses behave exactly as before; no database, no state.

### Key flow / sequence

Agent calls `autotask_get_ticket_attachment` → `_attachment()` → (includeData false) parent-scoped GET, else/fallback `GET /TicketAttachments/{id}` → `single_record()` takes the record from `item` or `items` → ownership check against `ticketID`/`parentID` → strip `data`, apply size cap → JSON result.

### Non-functional

- **Idempotency/concurrency**: pure read; unchanged.
- **Performance**: no extra request; the helper is O(n) over a list that holds one record.
- **Security**: credentials still only from request headers (`AGENTS.md`); the ownership check keeps one ticket's attachment id from being read through another ticket; no new logging of attachment data.
- **Multi-tenant isolation**: unchanged; the helper is a pure function with no shared state.
- **Observability**: errors keep the existing envelope; the not_found message is unchanged.

### Rollout & rollback

No feature flag. Merge to `main`, publish to INT (`references/mcp-track.md`); rollback is redeploying the previous `main`. Single repo (`Track: vendor-mcp`), no release-order dependency; nothing in the gateway or platform changes. Re-verification on a real zone needs the Forte or demo Autotask account (not available to the pipeline).

### Test strategy

respx-mocked tests in `tests/test_handlers.py`: metadata and data reads for the `items` shape, the `item` shape regression, ownership mismatch, empty `items`, the note-attachment variant, and a by-id read of another entity through `get_item()`. The existing baseline test (`tests/test_tools.py`) must stay green. Manual: one real-account read of a PDF attachment (needs a vendor account).

### Effort & breakdown

Story points: 1
Tier 1 (a few related fixes in one connector): one helper, two call sites, about six tests, one changelog file. No new API, no data migration, no UI. Main uncertainty: the exact Autotask by-id shape, covered by accepting both. Order: helper, `get_item`, `_attachment`, tests, changelog.

### Risks & dependencies

- **Risk**: if Autotask also returns `items` for these endpoints with different field casing or without `id`, the first-element fallback still returns the record; ownership then relies on `ticketID`/`parentID` being present (skipped when absent, as today).
- **Dependencies**: none; single repo.
