## Requirement understanding

One line: Don Gonzales (Forte) wants an agent that reads a PDF attachment of an Autotask ticket to get the PDF's text, including filled form-field values and tables (each value next to its label), instead of base64, and a clear "no text found" message for an image-only PDF.

Why: after PRD-22216 `autotask_get_ticket_attachment` with `includeData=true` returns the file only as a base64 `data` string. The model cannot read text from base64, so Forte's onboarding agent cannot read the Technology Checklist PDF (the only source of the new hire's email address) and holds every request for a technician. Use-case blocker; Micus approved taking it now (2026-11-20). Autotask ticket attachments are the first scope; other connectors can reuse the behavior later. Out of scope: OCR, other connectors, Forte's agent logic, non-PDF files.

Success: on the demo Autotask (ticket 9111) a run that reads Fixture A returns every answer-key field with its exact value (form-field and table values, each table value next to its own label); Fixture B (image-only) gives a message naming the file that says no text was found, and the run continues; run detail shows text or a short note and never base64; the PNG attachment (id 46) is read as before.

## Product design

### Goals / Non-goals

Goals:
- When an agent reads a PDF attachment of an Autotask ticket (or ticket note) with `includeData=true`, the result carries the PDF's readable text: filled form-field values (each with its label) and table rows (a row's label and values on one line), instead of the base64 content.
- An image-only PDF (no text layer, no form values) gives a clear message that names the file and says no text was found; the tool call succeeds so the run continues.
- A PDF that cannot be read (corrupt, password-protected, too large) gives a clear message naming the file, not an error that stops the run.
- Non-PDF attachments behave exactly as today (images keep returning base64).
- The extraction is a self-contained module with no Autotask dependency, so another connector can reuse it.

Non-goals:
- No OCR of scanned PDFs.
- No other connectors (Halo, ConnectWise, Microsoft 365 mail) and no platform runtime or UI change in this card.
- No change to Forte's agent logic (form pre-fill, email-domain check).
- No new tool, no renamed or removed tool or parameter, no new required parameter (`AGENTS.md`, `tests/test_tools.py`).
- No change to attachment search or creation, or to the ownership check.

### Behavior

For a PDF attachment, `autotask_get_ticket_attachment` / `autotask_get_ticket_note_attachment` with `includeData=true` returns the attachment metadata plus:
- `text`: the extracted text (form fields first as `- <label>: <value>` lines, then the page text, table rows as `Label | Value`).
- `textFound` (true/false), `pages`, `formFields` (count), `textTruncated` when cut.
- `summary`: one short line, e.g. `Text read from new-hire-form.pdf - 2 pages - 6 form fields`.
- No `data`. For an image-only PDF: `textFound: false` and `message`: `No text found in scan-0042.pdf (image-only PDF, 1 page). OCR is not supported. The attachment content is not returned.`
- Opt-out: new optional `includeRawPdf=true` returns the base64 `data` for a PDF as before (for an agent that wants the raw file).
- Optional `maxTextChars` (default 60,000, minimum 1,000) caps the returned text.

### Acceptance criteria AC1..AC9

- **AC1**: Given a text PDF with filled form fields, when the tool is called with `includeData=true`, then `text` contains every filled field with its label and exact value (checkboxes as `checked` / `not checked`), and the result has no `data` key.
- **AC2**: Given a PDF with a table, when read, then each row appears on one line with its label and its values separated by ` | ` (label next to its own value, not displaced to another row).
- **AC3**: Given form fields whose internal names are generic (for example `Text1`), when read, then the label shown is the field's tooltip if it has one, else the nearest text to the left of the field on the same line, else the nearest text above it, else the internal name.
- **AC4**: Given an image-only PDF (no text layer, no filled form field), when read, then the result is a success with `textFound: false` and a `message` that contains the file name and the words "No text found"; the result has no `data` key.
- **AC5**: Given any readable PDF, when the step is recorded in run detail, then the tool result is the extracted text or the short note, and contains no base64 content.
- **AC6**: Given a non-PDF attachment (the PNG, ticket 9111 attachment 46), when read with `includeData=true`, then the result is exactly as before (base64 `data`, `dataOmittedReason` rules unchanged).
- **AC7**: Given a PDF attachment, when `includeRawPdf=true` is passed, then the result returns `data` as before and no extraction runs.
- **AC8**: Given a PDF that is corrupt, password-protected, larger than 10 MiB decoded, or has more than 100 pages, when read, then the tool does not raise: it returns a message naming the file and the reason (for more than 100 pages the text of the first 100 pages plus a note), and never returns the raw base64 in place of the text.
- **AC9**: Given extracted text longer than `maxTextChars`, when read, then `text` is cut at the limit and `textTruncated` is true with the full length reported.

## Tech design

### Conclusion

Extract the text inside the Autotask connector, at the one place that already handles attachment content: `_attachment()` in `attachments.py`. A new self-contained module `src/autotask_mcp/pdf_text.py` turns PDF bytes into a small result (text, counts, found flag) with `pypdf`; `_attachment()` calls it when the decoded content starts with `%PDF-`, and returns that result instead of `data`. Both attachment tools (ticket and ticket note) get it through the shared function. Non-PDF content takes the existing path untouched.

### Where the current implementation lives

- `src/autotask_mcp/tools/attachments.py:33-65` - `_attachment()`: reads the record, pops `data`, applies the base64 cap, returns JSON.
- `src/autotask_mcp/tools/attachments.py:21-30` - the inline cap constants and the `includeData` / `maxInlineBase64Bytes` option definitions (pattern for the new options).
- `src/autotask_mcp/_json.py:29-47` - `dump()` result size cap.
- `tests/test_handlers.py:544-585` - the existing attachment tests (pattern for the new ones).

### Option analysis

| Option | Approach | Pros | Cost | Verdict |
|---|---|---|---|---|
| A. Extract in the Autotask connector (`pdf_text.py` + `_attachment()`) | PDF bytes are decoded where they arrive; result returned as text | Smallest change; fully in one repo; MCP flow (merge, INT publish) is quick; step trace shows text with no platform change; never sends megabytes of base64 through the model | A new dependency; each connector that wants it copies the module | **Chosen** (Autotask is the first scope) |
| B. Extract once in the agent runtime (`mb-platform-agentos`), for every connector | A middleware finds base64 file content in connector results and replaces it with text | Reusable by every connector | Connector results are plain text with no content-type contract, so it has to guess which strings are PDFs; runs after the base64 is already in the tool result; touches the shared platform runtime (framework-level change, Architecture A-rules); much larger blast radius for a first slice | Rejected for this card; listed as a follow-up if more connectors need it |
| C. Let the agent decode in the sandbox (pypdf is there) | Prompt/skill guidance | No code | Base64 up to 750k characters must travel through the model context; the offloaded-file path is unverified; not deterministic | Rejected |
| D. `pdfplumber` for tables | Real table detection | Better tables on complex layouts | Pulls `pdfminer.six` and Pillow; heavier; layout text keeps one row per line which is what the Done-when needs | Not chosen; fallback if the spike on the dummy fixtures shows pypdf layout is not enough |
| E. PyMuPDF | Fast, good tables | AGPL licence | Licence not acceptable | Rejected |

### Change list

- `pyproject.toml` / `uv.lock` **[changed]** - `uv add pypdf` (BSD-3, pure Python); `uv add --dev reportlab` (BSD, test fixtures only).
- `src/autotask_mcp/pdf_text.py` **[new]** - no Autotask imports. `read_pdf(raw: bytes, name: str, *, max_chars: int) -> PdfText` (dataclass: `text`, `found`, `pages`, `form_fields`, `truncated`, `length`, `message`). Steps: `PdfReader(BytesIO(raw))`; if encrypted try the empty password, else message "password-protected"; form fields from `reader.get_fields()` rendered as `- <label>: <value>` (checkbox `/Yes` as `checked`, `/Off` as `not checked`; empty values skipped); label = field `/TU` tooltip, else the field name when it is not generic (`^(text|check box|checkbox|field|combo box|list box|radio button)[ _-]?\d*$`, case-insensitive), else the nearest text left of the widget rectangle on the same line, else the nearest text above it (text fragments and positions from `page.extract_text(visitor_text=...)`), else the field name; page text from `page.extract_text(extraction_mode="layout")` per page, then each line with runs of 3+ spaces turned into ` | `, trailing spaces removed, blank-line runs collapsed; at most 100 pages (a note lists the skipped count); `found` is true when there is any form value or any non-blank page text; text cut at `max_chars` with `truncated` and the full `length`. Any `pypdf` exception becomes `found=False` with `message` "could not be read: <short reason>" (no stack trace, no content).
- `src/autotask_mcp/tools/attachments.py` **[changed]** - in `_attachment()` after `data = item.pop("data", None)`: when `includeData` and not `includeRawPdf` and `_is_pdf(data)` (decode only the first 16 base64 characters and compare with `%PDF-`, so non-PDF content costs nothing): if the base64 is longer than 14,000,000 characters (10 MiB decoded) return `message` naming the file and the limit; else decode, run `read_pdf` in `asyncio.to_thread` under `asyncio.wait_for(..., 20)` (a timeout becomes a message), and put `text` / `textFound` / `pages` / `formFields` / `textTruncated` / `summary` / `message` into the output; no `data`; `_json.dump(out, max_chars=max_text + 5_000)`. - `tests/test_pdf_text.py` **[new]** - builds PDFs with `reportlab` (AcroForm text fields and a checkbox, drawn table rows, an image-only page, generic field names); covers AC1-AC4, AC8, AC9 on the module. Dummy data only.

### Reuse & cleanup

- **Reuse**: `pypdf` (maintained open source, pure Python, already the library the platform sandbox uses for PDFs) instead of hand-written PDF parsing; the `Opt` registrar, `_json.dump`, `run()` error envelope and `respx` test setup already in the repo; `asyncio.to_thread` from the standard library.
- **New dependencies**: `pypdf` (runtime), `reportlab` (dev only, to generate test PDFs; the alternative of committing binary fixtures was rejected so that the fixtures are readable code and need no real documents).
- **API/method signatures**: one new module function `read_pdf(raw, name, *, max_chars)`; two new optional tool parameters (`includeRawPdf`, `maxTextChars`) on the two existing tools; no existing signature changes.
- **In-scope cleanup**: none needed in `attachments.py` (no dead code or unused constants found in the touched file).
- **Suggested follow-ups (out of scope)**: reuse in other connectors (copy `pdf_text.py`, or extract a shared package, or move it to the runtime as option B); OCR for scanned PDFs; a table count in run detail and the collapsible text block from prototype v83 (UI card).

### Data & API contract

Request (existing tool, one new optional parameter shown):

```json
{"ticketId": 9111, "attachmentId": 61, "includeData": true}
```

Response for a text PDF:

```json
{"id": 61, "title": "new-hire-form.pdf", "contentType": "application/pdf",
 "textFound": true, "pages": 2, "formFields": 6,
 "summary": "Text read from new-hire-form.pdf - 2 pages - 6 form fields",
 "text": "Form fields:\n- Full name: Jane Example\n- Email: jane.example@example.test\n...\n\nPage 1\nDivision | North\nLicense | Business Premium"}
```

Response for an image-only PDF (a success, not an error):

```json
{"id": 62, "title": "scan-0042.pdf", "textFound": false, "pages": 1,
 "message": "No text found in scan-0042.pdf (image-only PDF, 1 page). OCR is not supported. The attachment content is not returned."}
```

Unreadable or too large: same shape with `textFound: false` and a `message` naming the file and the reason. Non-PDF: unchanged. `includeRawPdf=true`: unchanged base64 behavior. `maxTextChars`: default 60,000, minimum 1,000. Downstream Autotask calls are unchanged. Backward compatibility: a consumer that expected base64 `data` for a PDF now gets `text` unless it passes `includeRawPdf=true`; this is the behavior the ticket asks for. No database, no stored state.

### Key flow / sequence

Agent calls the tool with `includeData=true` -> `_attachment()` reads the record (unchanged) -> content starts with `%PDF-`? no: unchanged path (cap, `data`). yes: size check -> `read_pdf` in a worker thread (20 s limit) -> result fields -> `_json.dump` -> the platform records the result in the step trace as returned.

### Non-functional

- **Idempotency/concurrency**: pure read; unchanged. Extraction runs in a worker thread so the event loop is not blocked.
- **Performance**: a 10 MiB / 100-page PDF is the ceiling (decode, parse, 20 s timeout); text returned is far smaller than the base64 it replaces (60,000 characters at most versus up to 750,000). Non-PDF content costs a 16-character decode.
- **Security**: untrusted file bytes are parsed by pure-Python `pypdf` (no JavaScript, no external fetch, no shelling out); limits on size, pages and output; credentials still only from request headers (`AGENTS.md`); file content and extracted text are never logged (only file name, page count and error class on failure); error messages carry a short reason, not content. Prompt-injection note: extracted text is untrusted content returned in a tool result like any other attachment text.
- **Multi-tenant isolation**: stateless and per-request; the ownership check (attachment must belong to the ticket / note) runs before any extraction and is unchanged; `pdf_text.py` holds no module-level state.
- **Observability**: failures use the existing error envelope or a `message`; one log line per unreadable PDF (file name, class of error).

### Effort & breakdown

Story points: 2
Tier: new behavior with a new contract in one connector (row "2": new contract, some unknown), not a single small fix (row "1").
Considerations: 1 repo / 1 new module + 1 changed module; new feature on an existing tool; no external API call added; read-only (no writes, no destructive action); no migration; untrusted file parsing and size limits are the security surface; no UI; 17 test cases.

Order inside this ticket: 1) dependency and `pdf_text.py` with tests on generated PDFs 2) wire into `_attachment()` and handler tests 3) options, baseline, README, changelog.

### Risks & dependencies

- **Risk**: pypdf layout extraction can merge or reorder columns on complex layouts. Mitigation: tests on table rows; fallback to `pdfplumber`; the form fields (the main data) come from the AcroForm values, not from layout.
- **Risk**: a consumer relying on base64 for PDFs. Mitigation: `includeRawPdf=true`, documented in the tool description, README and changelog.
- **Risk**: malformed or hostile PDFs. Mitigation: size, page, time and output limits; exceptions become messages.
- **Dependencies**: none blocking (PRD-22216 is released). New library `pypdf`. Demo Autotask credentials are needed only for the manual cases.
